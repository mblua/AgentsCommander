## 1. Objective and product contract

Add a deterministic, schema-versioned text file at each project's canonical `.ac/seed-manifest.toml`. It records the current set of project-scoped files that an in-scope AgentsCommander publisher actually published and the UTC wall-clock time of each file's most recent successful physical publication.

The v1 contract is:

1. One row per project-relative logical destination path, never an append-only event log.
2. Only an explicit typed `Published` outcome can add a row or change `last_seeded_at`.
3. A successful physical replacement sets time from that publication even when the replacement bytes equal the prior bytes. The physical publisher captures the clock at the target commit point itself, immediately after the successful create/link/replace/install syscall and before temp/trash cleanup, directory sync, logging, or any outer state persistence. V1 records milliseconds; two publications inside the same UTC millisecond can therefore have the same representable value and produce no textual rewrite when every other field is unchanged.
4. Observation, equal-default adoption, `AlreadyPresent`, `AlreadyCurrent`, skip, ordinary failure with no committed target/lifecycle effect, lost race, read, and scan do not change the manifest. A separately typed failed-after-logical-removal outcome may only delete the now-staged-away prior scope; it never adds a row or changes time.
5. A directory publication replaces its whole manifest scope in one transaction, using the exact regular-file list accumulated from the staging tree that was installed.
6. The file is safe for Git review: stable path, stable header, stable field and row order, LF, one final newline, no absolute machine or source paths, and no no-op rewrites.
7. The manifest is diagnostic, user-editable metadata. It never grants ownership and never authorizes overwrite, repair, or deletion.
8. Existing `.agentscommander-context-templates.json` hash and user-edit safety remains authoritative and unchanged in meaning.

The initial user-visible surface is the file itself. There is no Tauri command, TypeScript type, frontend listener, CLI query, web endpoint, or GUI in this Epic.

### 4.2 V1 TOML

The serializer emits this exact shape and field order:

```toml
# Managed by AgentsCommander. Diagnostic only; never grants file ownership.
schema_version = 1
coverage_version = 1
coverage = ["project_context_templates", "replica_config_folders"]

[[files]]
path = ".ac/Context.AgentsCommander.md"

source = "workspace_base"
last_seeded_at = "2026-07-16T19:41:12.456Z"
```

The exact canonical empty encoding produced by the same wire struct is:

```toml
# Managed by AgentsCommander. Diagnostic only; never grants file ownership.
schema_version = 1
coverage_version = 1
coverage = ["project_context_templates", "replica_config_folders"]
files = []
```

All four top-level fields are required, including `files`; do not add serde defaults that make a missing field valid. Coverage values and order must match exactly. For a nonempty vector, `toml` 0.8 emits the `[[files]]` array-of-tables form shown above instead of `files = []`.

Allowed v1 values are closed enums:

- `kind`: `project_context_template`, `replica_config_file`.
- Context `scope`: `context:agentscommander`, `context:coordinator`.
- Config scope: `config:` plus the UTF-8 project-relative destination directory using `/` separators.
- `source`: `builtin`, `workspace_profile`, `workspace_base`, `matrix_profile`, `matrix_base`, `catalog_default`.
- `path_encoding`: `utf8`, `unix_bytes_hex`, `windows_utf16_hex`.

The schema intentionally omits content hashes, file size, absolute project path, source path, profile letter, host, user, process id, operation history, and observed existence. Existing context ownership hashes stay in their specialized JSON file.

V1 applies explicit resource bounds: canonical file size at most 128 MiB, at most 250,000 rows, and at most 256 KiB of UTF-8 text in the decoded wire value of any `path` or `scope` field. Enforce the byte cap before an unbounded read allocation by opening the canonical file without following links and reading through `take(128 MiB + 1)`; reject the extra byte. With `toml` 0.8, row and string limits cannot honestly be guaranteed before parser allocation. A custom serde visitor for `files` rejects the 250,001st row, and row visitors reject a decoded `path` or `scope` immediately when its UTF-8 byte length exceeds 256 KiB; post-parse validation repeats all three checks as defense in depth. The 128 MiB cap is the hard parser input-size envelope, not a claim that parser working memory equals input size; the second raw conflict comparison must stream against the retained snapshot through a fixed-size buffer rather than allocating another 128 MiB copy. Activation is blocked unless adversarial near-cap valid and invalid TOML, including many tiny tables, large escaped strings, deep arrays, duplicate headers, and early/late syntax errors, stays within the same 512 MiB additional-working-set limit as the 100k-row acceptance run and returns a typed error rather than aborting the process.

The same bounds apply outbound before allocating the wire `Vec` or TOML `String`. Config path collection uses checked arithmetic and an exact TOML-escaped-length counter for the fixed v1 wire layout. It retains `Exact(Vec<PathBuf>)` only while the per-field, 250,000-row, and 128 MiB prospective-scope budgets remain valid; on first overflow it drops the accumulated identities, switches to `OverBound { reason, observed_at_least }`, and continues staging without further manifest-list growth so fail-soft target behavior is preserved. After merge, compute the exact full canonical byte length with checked arithmetic before serialization. If the complete manifest would exceed a bound, do not serialize the unrecordable batch: a successful target remains a carried publication, the pure mutation removes that publication's now-replaced prior scope from a valid canonical snapshot, the writer attempts at most that bounded removal transaction, records no new rows/time, and reports `PublishedUnrecorded(ResourceBound)`. If the removal write also fails, preserve the canonical bytes and report the persistence failure with the stale scope. Never retain the prior scope by design as though it survived a successful replacement, never truncate the installed file list, and never backfill the unrecorded publication later. These bounds leave the required 100k-row acceptance case inside the contract.

### 4.3 Deterministic serialization

1. Parse into dedicated `SeedManifestWire` and `SeedManifestRowWire` serde structs, each with `deny_unknown_fields`; do not deserialize through `HashMap` or serialize the internal keyed map directly. Declare fields in the exact wire order shown above. TOML duplicate scalar keys, duplicate table declarations, and scalar/table type redefinitions are hard parse errors, not last-one-wins input.
2. Validate the fixed schema and coverage values before allowing a write.
3. Represent `kind`, `source`, and `path_encoding` as closed serde enums. Internally key rows by `(path_encoding, path)`. Reject duplicate keys, invalid enums, malformed timestamps, mismatched kind/scope/source combinations, and a config row outside its declared scope. Every row in one config scope must also have the same `source` and byte-identical canonical `last_seeded_at`; mixed-source or mixed-time batches could not have been produced by the declared one-swap publication and make the whole canonical file read-only.
4. Sort rows by the serialized tuple `(path_encoding, path)` using bytewise ascending order. Do not sort by timestamp, source, locale, filesystem case rules, or discovery order.
5. Convert the sorted internal rows into a `Vec<SeedManifestRowWire>` and serialize the wire structs with the pinned `toml` 0.8 dependency. Golden fixtures pin the resulting byte layout so a dependency upgrade cannot silently change Git output.
6. Format time with `SecondsFormat::Millis` in UTC, always a quoted RFC 3339 string ending in `Z`. On read, parse RFC 3339, convert to UTC with that formatter, and require byte equality with the input. Reject alternative but equivalent spellings such as `+00:00`, missing milliseconds, or excess fractional precision.
7. Emit LF only and exactly one final newline. `.gitattributes` already fixes `*.toml text eol=lf`.
8. Prepend the same one-line managed comment on every write.
9. If the serialized bytes equal the existing canonical bytes, do not create a temp or replace the file. A real publication normally changes a timestamp; lifecycle cleanup may legitimately be a no-op.

### 4.4 Lossless path representation

The logical path is always relative to the project root and begins with the `.ac` component. It never contains an absolute prefix, drive, UNC share, `.` component, `..` component, NUL, or an empty component. Separators in the manifest are `/`. No Unicode normalization or case folding is applied.

- If every native component is valid Unicode, write the readable project-relative path and `path_encoding = "utf8"`.
- On Unix, if any native component is not UTF-8, encode the complete normalized project-relative native byte sequence as lowercase, two-hex-digits-per-byte text and set `path_encoding = "unix_bytes_hex"`. Insert byte `2f` between components.
- On Windows, if any native component is not valid Unicode because it contains unpaired UTF-16 code units, encode the complete normalized project-relative UTF-16 sequence as lowercase, four-hex-digits-per-code-unit text and set `path_encoding = "windows_utf16_hex"`. Insert code unit `002f` between components.

Encoding is selected canonically: use `utf8` whenever lossless Unicode conversion succeeds, otherwise the platform-native hex form. `unix_bytes_hex` must be lowercase fixed-width hex, use `2f` only as the component separator, and decode to at least one invalid UTF-8 sequence; otherwise `utf8` was the canonical encoding and the row is rejected. `windows_utf16_hex` must be lowercase fixed-width hex, use `002f` as the separator, and decode to at least one unpaired surrogate for the same reason. Decoded components must contain no empty, `.`, `..`, separator, or NUL component. The parser understands and preserves all three known forms on every platform, including a foreign-platform row checked out through Git. A foreign encoded row is metadata only and is never converted into a filesystem target.

Validation and lifecycle prefix filtering operate on a decoded component representation, separately for UTF-8, Unix bytes, and Windows UTF-16, never on serialized string prefixes. Config scope text is always UTF-8 and must have exactly `config:.ac/<validated-wg>/<validated-__agent>/<validated-dest>`: reuse the pure workgroup/replica name rules and `validate_config_seed_dest`, which requires one folder component. Every config row path must be a strict component-wise descendant of its declared scope. Context rows must match one of the two exact allowed UTF-8 path, scope, kind, and builtin-source combinations. Foreign native-hex rows remain filterable by converting the validated UTF-8 scope/prefix components into the row variant and comparing components without filesystem access. Team/agent committed-intent filters parse those validated structured workgroup/replica components; they never use lossy suffix, substring, or serialized-prefix matching.

Hardlinks at two relative paths are two logical rows. Case spelling is preserved so Windows case-sensitive directories are not collapsed. Project move and clone need no owner rebind because the identity is project-relative and the manifest travels with the project.

## 5. Publication outcomes and time semantics

### 5.1 Shared outcome rule

Every included boundary must expose a typed result after the real target commit. The following is a semantic vocabulary, not one catch-all production enum:

```text
Published { project_ac_root, kind, scope, source, files, published_at }
AlreadyPresent | AlreadyCurrent | Observed
Skipped { reason }
Failed { error }
```

`Published` means the target publication syscall returned success and any synchronous rollback owned by that publisher is no longer pending. The boundary that executes that syscall captures `published_at` once immediately after success, before cleanup, directory sync, logging, or return; a caller or recorder is forbidden to call `Utc::now()` after the helper returns and label that later observation as publication time. It is wall-clock display data, not a conflict-resolution key. Do not synthetically increment it on a same-millisecond event or clock rollback. Lock order, not `max(timestamp)`, determines which same-scope publication is later.

Production types remain boundary-specific so callers cannot construct impossible combinations:

| Boundary | Required typed surface |
| --- | --- |
| Create-only context link | `Result<CreateOnlyPublication, String>` where `CreateOnlyPublication::{Published { published_at }, AlreadyPresent}`. The hard-link helper captures the injected clock after the winning `hard_link` and before unlinking its temp. |
| Recognized context replacement | `TemplatePublication::{Published(ContextPublication { published_at }), AlreadyCurrent, ChangedUnderUs, Observed, Skipped(reason)}` plus the crate-private two-channel `ContextTemplateExecution<T> { completion: Result<T, String>, published: Option<ContextPublication> }`. The atomic-replace primitive captures the injected clock before parent-directory sync or return. |
| Config folder | `ConfigSeedReport::{Published(ConfigSeedPublication), Skipped(ConfigSeedSkipReason), Failed(ConfigSeedFailure), FailedAfterLogicalRemoval(ConfigSeedRollbackFailure)}`. `ConfigSeedPublication.files` is `CollectedSeedFiles::{Exact(Vec<PathBuf>), OverBound { reason, observed_at_least }}`; the last report variant is not publication and can only carry a proven prior-scope removal. |
| Manifest transaction after a target commit | `ManifestRecordOutcome::{Recorded, Unchanged, PublishedUnrecorded(ManifestDegradedReason)}`; `Unchanged` means no canonical byte change, such as a lifecycle no-op or an otherwise identical same-millisecond row. It never erases the target's separate `Published` truth. |

Only a boundary-specific physical publisher invoked with a coordinator-created `ProjectPublicationPermit<'_>` may construct `Published`; its constructors remain private to the boundary module. The permit has exactly `Tracked(&mut ProjectSeedManifestGuard)` and `DegradedUntracked { held_guard: Option<&mut ProjectSeedManifestGuard>, reason: ManifestDegradedReason }`. `Tracked` is the only variant allowed to invoke the recorder. `DegradedUntracked` exists only for the two frozen cases in section 6.1: a pre-contention lock capability/I/O error with no guard, or a corrupt/future canonical snapshot while the successfully acquired guard remains held. A timeout or later error after observed contention and every unsafe/reparse/identity failure constructs no permit and cannot mutate the target. Thus a physical publisher can truthfully return commit-point `Published` in a classified unrecorded mode without pretending a guard exists, while no caller can downgrade a known race into untracked publication. The event carries the timestamp captured at the commit point. A recorder never manufactures the time with its own later `Utc::now()`, and no caller converts generic `Ok(())` into `Published`. Cleanup and specialized-state errors after the commit may make the outer operation return an error, but they cannot erase the carried publication or prevent its immediate manifest attempt when the permit is `Tracked`. Do not model a context target as `Result<(T, Option<ContextPublication>), String>`: a later `?` would erase a publication on the error branch. `ContextTemplateExecution` deliberately carries `completion` and `published` independently; it is internal only and never crosses IPC.

Internal manifest failures use a `thiserror`-derived `SeedManifestError` with distinct unsafe-path, busy-timeout, lock-capability/I/O, bounded-read, outbound-resource-bound, strict-parse/validation, external-edit-conflict, temp-write/sync, atomic-replace, Windows partial-replace, Windows post-success identity-conflict, and recovery-required variants. A Windows publication error retains the raw `u32` error before any inspection call and carries the expected and observed path/identity state defined in section 6.2. Automatic flows convert those into `ManifestDegradedReason` and structured logs; existing Tauri command boundaries convert to `String` only at their current IPC edge. Do not flatten lock contention, unsupported locking, corrupt input, over-bound output, post-target persistence failure, or a partial namespace outcome into one message or boolean.

A physical replace with identical bytes is a publication and sets time from the new event. In particular, config-seed tiers 1 through 4 replace their destination on every successful spawn, so every file row in that scope receives that event's shared timestamp even if the staged bytes are identical. This normally creates high Git churn; a same-millisecond event can serialize identically. Catalog-default remains absent-only.

### 5.2 Project contexts

`session_context::write_template_if_missing` and its test seam return `Result<CreateOnlyPublication, String>`, with timestamp-bearing `Published` only for the hard-link winner and `AlreadyPresent` for the `AlreadyExists` loser. They must never infer publication from final file existence or equal bytes. An injected clock at the hard-link boundary proves cleanup delay cannot shift the recorded time.

`seeded_context_templates` separates its ownership/hash state from publication events:

- Equal-default observation may still call the existing hash-state `mark_seeded`; it emits no timestamp event.
- `create_missing_template` propagates the create-only outcome.
- `auto_update_generated_template` returns timestamp-bearing `Published`, `ChangedUnderUs`, or failure after its re-read and atomic replace.
- `sync_one_template` returns both its existing pending-update result and an explicit optional publication, so callers cannot collapse an actual update into generic `Ok`.
- `overwrite_context_template_with_default` records only after the backup, final revalidation, and atomic replacement succeed.
- `heal_stale_global_context_template` returns a typed internal outcome instead of logging all branches into `()`; only its successful atomic replacement records, using the time carried from that replace.

Every item above is a one-target operation. The high-level coordinator consumes `ContextTemplateExecution.published` while it still owns the borrowed project transaction, attempts the manifest update immediately, and only then propagates `completion` with `?`, persists specialized state, or advances to the next template. Never accumulate context publications in a vector for replay after the loop. `sync_one_template` therefore returns `TemplateSyncOutcome { pending_update, target_outcome }` inside the two-channel envelope; create/update helpers preserve `published: Some(...)` if their post-commit validation or cleanup reports an error. Automatic ensure/scan/read loops record each successful target before their existing best-effort state save. Explicit overwrite performs backup and final revalidation, records the returned publication, then runs `mark_seeded` plus `persist_state_strict`; its existing public `Result<ContextTemplateOverwriteResult, String>` is derived from `completion` only after the internal publication has been handled, so a strict state-save error remains an IPC error without losing the truthful manifest attempt.

Coordinator upgrades must cover every current recognized generated-default path, not only one historical step. A pristine frozen-v2 coordinator loaded without seeded state publishes current v4 directly. A pristine frozen-v3 coordinator loaded without seeded state publishes current v4 directly. A seeded pristine-v3 coordinator publishes v4 and then advances the specialized state version from 3 to 4. All three physical replacements return the same typed commit-point `Published(ContextPublication { published_at })` surface as other recognized updates; state persistence, version bump, or outer-call failure after replacement cannot create, delay, or retract that publication evidence. Global v1-to-v2 and Root v5 behavior remain separately covered.

For every context mutation, acquire the project gate before the final target re-read, backup, hard-link, or atomic replace, revalidate the pinned `.ac` owner and target parent under that gate, and hold it through the manifest transaction. Acquiring only after receiving `Published` is incorrect: two processes can publish A then B but record B then A, leaving the manifest scope ordered differently from the target. Explicit overwrite returns a retryable busy error before creating a backup or changing the target. Automatic session/discovery flows skip disk publication on timeout and use the existing file or an in-memory default; they never publish outside the gate after known contention.

`read_or_create_context_template` must not fall back to a direct ungated `write_template_if_missing` for either managed project filename when synchronization skipped or failed. The synchronized path owns publication; if it cannot publish and the file is still absent, return the in-memory default. `migrate_legacy_agent_context_template_with` remains an unrecorded user-content migration as excluded in section 3.2.

The manifest update happens after the target publish and before or independently of the specialized hash-state persistence. A hash-state failure never retracts a real publication. A manifest failure never changes hash ownership decisions. Fresh project creation treats every gate acquisition/capability/unsafe-path failure as setup failure and never registers or mutates templates without a working project gate. Once `create_dir` makes `.ac` visible, no failure path recursively removes that root, even after this caller acquires the gate and the directory identity still matches. The gate and persistent lock are inside the published root: another caller can acquire and release that same gate between the creator's `create_dir` and acquisition, publish a template or complete setup, and leave the root identity unchanged. Creation intent, later gate ownership, exact identity, unchanged known files, and lack of observed contention therefore cannot prove exclusive rollback authority. On any later setup failure, leave the root unregistered, preserve every truthfully published template and manifest row, and clean only operation-owned temporary files through their existing identity proof; never delete `.ac`, its persistent lock, user content, or possible contender output. A later explicit `new_project` registration call re-runs ensure rather than trusting mere `.ac` existence. The separate bare `create_ac_project` command retains its current rule that a pre-existing `.ac` is not backfilled, so retrying that command alone after a fresh partial failure preserves the partial state; this limitation is explicit and cannot be represented as successful repair. A successful registration still requires both templates to have completed under the gate.

Current async session/discovery callers must not block a Tokio worker for the gate's 10-second polling loop. Move the complete synchronous context materialization call into blocking work with cloned owned arguments. `discover_ac_agents` and `discover_project_inner` first clone the settings snapshot and drop its `RwLockReadGuard`, then run their synchronous scan/publication work in the same blocking wrapper. The async explicit-overwrite, new-project, and lifecycle commands use that wrapper for every gate-owning synchronous transaction too. No settings or session-manager guard may span a manifest wait.

Use one crate-private `async fn run_blocking_owned<F, T>(work: F) -> Result<T, BlockingTaskError>` wrapper around `tokio::task::spawn_blocking` for every ordinary, non-session-tracked #1038 blocking request, with the usual `F: FnOnce() -> T + Send + 'static` and `T: Send + 'static` bounds. `BlockingTaskError` is a `thiserror` enum with `Join(tokio::task::JoinError)` and `CanceledBeforeStart`. If the returned async future is dropped before its first poll, its body never schedules a task and drops `work` normally. Once first-polled, a shared atomic state has exactly `Queued | Started | Canceled`: the closure performs a `Queued -> Started` compare-exchange with `AcqRel` before invoking `work`, while the armed waiter drop guard performs `Queued -> Canceled` with `AcqRel`, observes the losing state with `Acquire`, and only then calls the `AbortHandle`. The closure observes `Canceled` with `Acquire` and returns an internal typed no-op without invoking `work` if Tokio polls it. The join mapping is exhaustive: a wrapper-returned no-op is `CanceledBeforeStart`; a canceled `JoinError` observed with state `Canceled` is also `CanceledBeforeStart` because Tokio may discard the queued task; every other `JoinError`, including panic after `Started`, is `Join`. The waiter guard is disarmed on every terminal join-result mapping, including the two cancellation forms and join failure.

This state gate, not abort alone, guarantees pre-start no-mutation because locked Tokio 1.51.0 documents that abort only may prevent an unstarted blocking task from running and cannot stop one already started. After `Started` wins, dropping the caller future necessarily drops its response `JoinHandle`, which Tokio defines as detaching the running task; the plan does not claim otherwise. The accepted safety property is narrower and testable: the already-started closure is self-owned and runs to completion, all target/metadata/rollback/temp cleanup and diagnostic probes are owned inside it, and no outer response owner is required for cleanup. Session-create work is different: it uses the tracker mutex as its sole start/accounting truth in section 6.3, so a started session closure remains represented through shutdown even if its response waiter disappears. The caller retains its existing typed inner result and adds operation context when mapping `BlockingTaskError` at the current command boundary.

### 5.4 Current-table and lifecycle semantics

V1 contains active rows only. It has no retired tombstones or history rows. Here, current means the last AC-declared membership of a successfully published scope in project history, not a live claim that every target still exists on this machine.

| Event | Exact manifest effect |
| --- | --- |
| Scope publish `{a,b}` then `{b,c}` | In one locked transaction, delete every prior row in that exact scope, then insert `b` and `c` with the new shared time. `a` disappears. `b` is updated, not duplicated. |
| Successful publication of an empty staged tree | Remove every prior row in that scope and add none. Keep an already-existing manifest as a valid empty v1 file. If the canonical manifest is absent and there are no rows to record, do not create a header-only file. |
| Source tier changes for the same destination | Same path and scope rows are replaced; `source` changes and time is set from the publication event. Wall-clock rollback means it is not required to increase. |
| AC removes one replica | After the replica is logically absent, remove every `replica_config_file` row whose config scope is under that replica prefix. |
| AC removes a workgroup | Remove every replica config scope under that workgroup after the user-visible workgroup path is gone. A hidden delete orphan does not keep the old logical scope active. |
| AC deletes a team | After the team directory commit, remove scopes for each workgroup whose directory removal succeeded and for valid matching team workgroup identities already absent at the explicit delete event. Preserve rows for each workgroup whose removal failed and whose original path remains. This is lifecycle intent from `delete_team`, not discovery-based `NotFound` pruning. |
| AC deletes an Agent Matrix and cascaded replicas | After metadata persistence commits, remove every decoded config scope whose validated replica component is that exact `__agent_<name>` in this project, including replicas already absent when the explicit delete began; preserve restored targets on a pre-commit rollback and prune only `StillStaged` targets there. The origin `_agent_*` directory has no v1 rows. |
| Manual file/directory deletion or edit | No change. The manifest records AC publication, not observed existence or current bytes. |
| Missing workgroup during discovery, offline share, access denial | No change and no automatic pruning. |
| Project archive, unarchive, unregister, or re-register | No change. Those operations retain the project and `.ac` on disk. |
| Project clone/copy | Preserve the committed manifest byte-for-byte. Do not invent a new owner id, reset times, backfill, or prune ignored workgroup paths that the clone lacks. |
| Project directory deletion outside AC | The manifest disappears with the project; there is no external cleanup registry. |
| Config `dest` changes | The old destination scope remains because AC did not remove it; the new destination gains a separate scope on its first real publication. |

Lifecycle filesystem ordering uses the same project gate as publication. Perform prompts, dirty checks, path collection, and the first public live-session check before waiting, with all settings/session/lifecycle/team-config guards released. A short preliminary `TeamConfigMutationGuard` may be used only to copy exact raw team bytes and intent into owned memory; it must be dropped before project-gate acquisition. The blocking commit then acquires the project gate first and, only for a path that mutates team configuration, acquires `TeamConfigMutationGuard` second. It re-reads and revalidates every mutable input under the final guards, holds the project gate across logical removal, rollback, and matching prune, and holds the team guard across every team-config read/commit/restore that participates in that transaction. Neither synchronous guard crosses `.await`. This total order prevents a stale spawn from recreating or recording a just-deleted replica and prevents a stale prepared team snapshot from overwriting a concurrent writer. Cleanup never deletes a row before the corresponding logical-removal commit; a failed rollback reports which targets remain staged and therefore are already logically absent. A lock timeout after known contention returns a retryable delete error before mutation. A pre-contention lock-capability error preserves today's deletion behavior as untracked degradation, but a reparse, identity mismatch, or unsafe canonical path fails closed before a still-reversible deletion. Exact boundaries are:

It holds both guards across the team-membership commit, typed replica removal, and manifest prune, then drops both before refresh or output. Prune only after `Removed` or explicit `AlreadyAbsent`. A plain `NotFound` observed during discovery never calls this path and never prunes. They acquire the project gate before the atomic rename, prune `Deleted` and `Partial` while still holding it, release it, and only then convert the structured outcome into their existing outer success/error contract. `Partial` means the original workgroup path was renamed away but hidden-orphan cleanup failed, so rows are no longer active even though the command still returns its partial-delete error. `Blocked` and `Other` preserve rows and release the gate before the GUI awaits blocker diagnostics or any caller formats or returns the error.

Replace its current `replica.exists()` branch with `symlink_metadata`: exact `ErrorKind::NotFound` means absent and adds no target, every other inspection error aborts preflight, and an existing entry must pass the existing non-reparse directory validation before its prefix is retained. After preflight, the blocking transaction acquires the project gate, stages targets, obtains the outer and inner pending-inclusive manager snapshot in that order, releases both manager reads, and only then acquires the team guard. Under project then team it re-reads every planned team config no-follow and requires exact prepared bytes before the first write. Any mismatch rolls back staged targets before mutation. The second live check uses `pub(crate) fn live_working_directories_for_deletion_blocking(&self) -> Vec<String>` on `SessionManager`: the caller first obtains the outer `Arc<tokio::sync::RwLock<SessionManager>>::blocking_read`, the method then obtains exactly one inner `SessionManagerState::blocking_read`, walks `state.order`, and returns cloned workdirs for every non-`Exited` row without filtering `state.pending_create`. ## 6. Cross-process persistence, lock order, and crash policy

### 6.1 Kernel lock protocol

`ProjectSeedManifestGuard::acquire` uses `.ac/.seed-manifest.lock` and this exact protocol:

1. Resolve the canonical project and `.ac` root without following the final component, open the `.ac` directory no-follow, validate a real non-reparse directory, and retain a stable directory identity for the guard (`st_dev` + `st_ino` on Unix; volume serial + file ID from the opened handle on Windows). Unix uses `O_DIRECTORY | O_NOFOLLOW`; Windows uses `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT` and explicit read/write/delete sharing so the retained identity remains observable across supported cooperating operations. A path spelling or `canonicalize` result alone is not an owner proof, and a stable identity is not exclusive new-project rollback authority. For config seed, ownership must first resolve through `wg_replica_layout_from_agent_dir`, then the original project/`.ac`/workgroup/replica chain is walked and pinned without following reparse components; the strict resolver is necessary but not sufficient by itself.
2. Open or create the lock file with `.read(true).write(true)`, never append or truncate. For an absent file use `create_new(true)`; if another process wins and returns `AlreadyExists`, retry the existing-file no-follow open rather than treating that create race as a lock failure. If an external process removes the name between attempts, retry the create/open state machine within the same deadline. On Windows set `FILE_FLAG_OPEN_REPARSE_POINT` plus explicit read/write/delete sharing through `std::os::windows::fs::OpenOptionsExt` and the already-direct `windows-sys` dependency. On Unix set `libc::O_NOFOLLOW` for every file open and `libc::O_DIRECTORY | libc::O_NOFOLLOW` for directory opens through `std::os::unix::fs::OpenOptionsExt`; add exactly `[target.'cfg(unix)'.dependencies] libc = "0.2"`. Validate the opened handle as regular and non-reparse and retain its stable file identity. This is a no-follow identity dependency, not a locking dependency.
3. Poll `File::try_lock()` on that single, un-cloned handle. Its Rust 1.93.1 signature is `Result<(), std::fs::TryLockError>`, so match `TryLockError::WouldBlock` and `TryLockError::Error(io_error)` exactly. Do not match `io::ErrorKind::WouldBlock`. Independent handles are covered by the lock contract; the unspecified case is calling lock again on the already-locked handle or a clone, which the outer-only/borrowed-guard design forbids.
4. Track `saw_contention`. Only `TryLockError::WouldBlock` proves a competing owner. Use one `Instant` deadline and sleep for `min(50 ms, remaining)` so controlled filesystem polling does not overshoot 10 seconds. At zero remaining, return a typed `BusyTimeout`. A single OS path-open call is synchronous and not cancellable by this loop; the 10-second total-return claim is mandatory only on the responsive local NTFS/Unix conformance filesystems, while opt-in network probes record open latency and make no bounded-return certification for a hung server/mount.
5. A timeout after contention skips an automatic target publication; an explicit overwrite or still-reversible lifecycle command returns a retryable busy error before mutation. `TryLockError::Error` is a typed capability/I/O failure, not contention. If it occurs before contention, automatic context/config publishers retain their existing fail-soft target behavior as `PublishedUnrecorded`, lifecycle commands retain their existing untracked removal behavior, explicit overwrite retains its existing overwrite behavior with a tracking warning, and new-project setup fails as specified in the table below. After observed contention, every path skips or fails before the target because racing is known. Reparse/non-regular paths always fail closed before project target mutation.
6. Immediately after locking, verify by no-follow path reopen that both `.ac` and `.seed-manifest.lock` still name the identities held by the guard. Repeat that check at each bounded commit boundary, not once per staged file: before a context target mutation; before config scratch sweep/staging begins and again before old-destination/install renames; before a lifecycle rename/remove; and before canonical manifest replacement. A mismatch before target commit is an unsafe-path skip/error; a mismatch after target commit is `PublishedUnrecorded`. These checks detect lock-file deletion/replacement and root substitution at the defined failpoints without adding per-file target I/O; they do not claim to defeat a hostile rename in the final instruction-level race after the last check.
7. The guard owns the only lock-file handle and pinned root identity through target publication or lifecycle commit and manifest update. Call `File::unlock()` explicitly, warn if explicit release reports an error, then drop the handle. Never clone or leak it to background work.

Architect dependency decision: **APPROVED**. The direct `libc = "0.2"` declaration is target-scoped to `cfg(unix)` in `src-tauri/Cargo.toml`. Production use is limited to the `O_NOFOLLOW` and `O_DIRECTORY` constants passed to safe `OpenOptionsExt::custom_flags` calls inside `config::seed_manifest`; it adds no raw libc syscall, no lock implementation, no cross-platform dependency, and no use outside the no-follow identity boundary. The standard library exposes `OpenOptionsExt` but not portable named constants for those Unix flags, so this narrow declaration is necessary to prevent symlink traversal at open time. No locking crate is approved.

Only outer publication/lifecycle coordinators acquire `ProjectSeedManifestGuard`. Low-level hard-link, atomic-replace, copy, and recorder helpers accept a borrowed transaction/guard or return typed outcomes; they never reacquire the same project lock. This prevents nested self-locking when `ensure`, read-sync, and self-heal helpers call one another.

Apply degraded outcomes consistently:

| Gate/manifest condition | Automatic context/config publication | Explicit context overwrite | Newly created `.ac` setup | Lifecycle command |
| --- | --- | --- | --- | --- |
| Timeout or later error after `saw_contention` | Skip disk target; use existing/in-memory context or continue PTY without config seed. | Retryable busy before backup/target. | Setup error; leave any just-created `.ac` unregistered before or after gate ownership. Preserve truthful partial output and never recursively delete the published root. | Retryable busy before a still-reversible logical removal; if reached only after an in-operation failed rollback, preserve that already-authoritative outcome and warn. |
| Lock capability/I/O error before any contention, or validly locked corrupt/future manifest | Preserve the existing primary target behavior but report `PublishedUnrecorded` if it publishes. | Preserve existing overwrite behavior but report success with a structured tracking warning. | Setup error leaves any just-created root unregistered; a validly locked corrupt/future manifest allows truthful untracked template publication because serialization still exists, and a later failure preserves that partial root. | Preserve removal and warn that rows may be stale. |
| Reparse/non-regular lock or canonical path, invalid `.ac` root, or pinned-identity mismatch | Fail closed before a target mutation. | Error before backup/target. | Setup error; preserve the created or pre-existing root and clean only this operation's identity-proved temporary files. | Error before a reversible removal; never undo an outcome that became irreversible through a failed rollback, and warn if its metadata cannot be pruned. |

The lock file is persistent and is never unlinked on `Drop`. Kernel ownership is released automatically on normal close and process death, so stale-owner recovery requires no PID, wall clock, age heuristic, or unsafe lock-file deletion. A leftover empty file is normal. This avoids PID reuse and the Unix split-inode race where deleting a locked path lets a second writer lock a new inode. A lock-unaware external deletion/replacement is detected by the handle-versus-path identity checks when it occurs before a defined check; the residual race after the last check is outside the cooperating-writer guarantee and is documented and tested as such.

The guarantee is cooperative among #1038-aware AC processes on a filesystem that implements the OS lock. Rust maps this API to `flock(LOCK_EX | LOCK_NB)` on Unix and `LockFileEx(LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY)` on Windows. Mandatory conformance covers local NTFS and the CI Unix local filesystem. Windows SMB3 documents byte-range locks, and modern Linux can emulate `flock` on NFS/CIFS, but behavior varies by server, dialect, mount, and failover mode. Unsupported or falsely cooperative filesystems follow the degraded policy and must not be advertised as safe. See the official [`File::try_lock`](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock), [`TryLockError`](https://doc.rust-lang.org/std/fs/enum.TryLockError.html), Windows [`LockFileEx`](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-lockfileex), and Linux [`flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html) contracts.

The Windows writer support claim is deliberately narrower than API availability:

| Windows environment | V1 status and claim |
| --- | --- |
| Windows 10 1809+ or Windows 11, local NTFS | Supported and mandatory. Stage E proves lock behavior, the `ReOpenFile` witness protocol, successful old-or-complete-new namespace visibility, long verbatim paths, and the certified DACL, ADS, creation-time, read-only, and compression metadata surface. EFS-encrypted files are outside that surface. Pre-publication data flush is required. No power-loss or namespace crash-durability claim is made. |
| Earlier Windows client, Windows Server, Wine, or compatibility layers | Outside the documented AgentsCommander client support matrix. The underlying APIs may exist, but #1038 makes no certification claim. |
| Local ReFS, CsvFS, FAT/FAT32, or exFAT | Not certified by v1. FAT-family filesystems also cannot satisfy the certified NTFS DACL, named-stream, and compression evidence. Calls that happen to succeed remain non-authoritative; no multiprocess, metadata, atomic-visibility, or durability claim is advertised. |
| UNC/SMB, including SMB 3.0, Transparent Failover, and Scale-out shares | Opt-in evidence only. `ReOpenFile`, `MoveFileExW`, and byte-range locking have documented SMB3 support, but server implementation, share mode, failover, and `ReplaceFileW` behavior are not certified together here. No 10-second path-open, metadata, atomic-visibility, or namespace-durability guarantee is claimed. |
| Unix NFS/CIFS or another network mount | Opt-in evidence only with exact server and mount options. No broader claim follows from one passing environment. |

This matrix limits the support claim, not the parser's portability or the diagnostic file's non-authoritative nature. The writer does not infer support merely because one syscall returned success. Every optional probe records OS build, filesystem name, local versus remote path, SMB dialect or mount options, and each API result separately.

The mandatory core NTFS metadata suite uses in-process `windows-sys` bindings, not localized shell output: `GetFileSecurityW`/`SetFileSecurityW` for the custom DACL and `DeviceIoControl(FSCTL_SET_COMPRESSION)` for both compression directions. Architect decision: EFS encryption preservation is unclaimed and out of scope for v1 because no exact capable fixture, account/certificate custody, or evidence owner exists. The implementation does not call `EncryptFileW`/`DecryptFileW`, auto-enroll a certificate, add an EFS fixture, create a skipped EFS gate, or describe incidental behavior on encrypted files as supported. This is a final scope exclusion, not an implementation choice.

An external editor, an older AC binary, or a filesystem that falsely reports lock support can violate cooperation; the manifest must never be treated as an authority because of that limitation.

### 6.2 Locked read, merge, and atomic write

The transaction begins after gate acquisition, before a guarded target mutation:

1. Stream at most 4096 sibling directory entries before creating this transaction's temp. A candidate is exact only when its filename parses as `.seed-manifest.<uuid>.tmp` and the UUID round-trips byte-for-byte through lowercase hyphenated `Uuid::parse_str(...).hyphenated()`. Retain at most the 4096 fixed-length exact names needed for later inspection, saturating counts, and at most 32 exact-name plus 32 malformed-lookalike diagnostic samples; stop enumeration at the entry budget and set `scan_truncated = true`. Never allocate or log once per directory entry. Entries beyond the budget and malformed lookalikes are untouched by construction. On Windows, classify every inventoried exact candidate as `WindowsPriorTempRecoveryCandidate`: without a durable transaction marker it is indistinguishable from the sole named complete object left by a prior 1176, 1177, or ambiguous failure. It is never reclassified as the current transaction's owned temp.
2. Load one `CanonicalSnapshot` before target mutation. Open the canonical path no-follow, validate the opened handle as regular/non-reparse, retain its identity, and read at most 128 MiB plus one byte. `NotFound` is an explicit absent snapshot and an empty v1 state; no other failure means empty. Preserve the exact raw bytes as well as the one parsed/validated internal state. On Windows retain the existing canonical handle with `GENERIC_READ` and `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` through publication as the destination identity witness. Record its file attributes. An existing `FILE_ATTRIBUTE_READONLY` canonical is a typed read-only snapshot: preserve it, create no temp, and report a target publication as unrecorded rather than clearing the bit. Before any no-op return or mutation, process the bounded inventory from step 1. On Windows, preserve every inventoried candidate regardless of canonical validity; uninspected entries are also preserved because cleanup is current-owned-only. On Unix, an absent, strict-invalid, unsafe, unreadable, recovery-required, or truncated inventory preserves every candidate; only a complete inventory plus a valid canonical permits removal after a no-follow open, stable path/handle identity, regular/non-reparse type, exactly one hard link, and an immediate second identity check. Close every inspected candidate handle. A directory, symlink, junction, reparse point, swapped identity, hard-linked file, or inspection error is preserved. Emit at most one aggregate diagnostic per transaction containing saturating observed counts, the bounded samples, and `scan_truncated`; never emit one warning per candidate.
3. If the snapshot is valid, apply exactly one pure mutation after the carried outcome's commit boundary: single-row upsert or complete-scope replacement for an exact `Published`; prior-scope removal with no insert for an over-bound `Published` or `FailedAfterLogicalRemoval`; or validated prefix/committed-intent removal for a lifecycle command. The mutation reports whether the row set changed. An ordinary `Skipped`/`Failed`/observation performs no mutation. If a permitted removal or empty-scope replacement changes no row, return `Unchanged` without serializing or creating a header-only manifest.
4. Compute the exact canonical output length with checked arithmetic before allocating the sorted wire vector or TOML string. If it exceeds any bound after an exact publication merge, drop the unrecordable new batch, retain only the pure removal of that publication's prior scope if any, recompute, and report `PublishedUnrecorded(ResourceBound)` after at most that removal write. Otherwise sort and serialize deterministic bytes only for a logical row change. If they equal an existing canonical snapshot, return `Unchanged` without creating a temp. A real target publication normally differs when its formatted timestamp or another field differs; a same-millisecond event can be a no-op.
5. If bytes changed, create `.seed-manifest.<uuid>.tmp` no-follow and create-new in the pinned `.ac` directory, retain its identity, write all bytes, flush, and `sync_all` the writer. On Unix use read/write plus `O_NOFOLLOW`. On Windows, `OpenOptions` must map to `CreateFileW` with `GENERIC_READ | GENERIC_WRITE`, `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, `CREATE_NEW`, and `FILE_FLAG_OPEN_REPARSE_POINT`; do not request `DELETE` merely to work around sharing. Require the writer handle and a no-follow path probe opened with `GENERIC_READ`, the same three share flags, `OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT` to report the same regular, non-reparse identity, exactly one hard link, and the exact expected length and bytes, then close that probe. A Windows temp must enumerate only its unnamed data stream before publication; an injected named stream is an unsafe substitution and aborts.
6. Immediately before publication, revalidate the pinned `.ac` and lock identities. For an existing canonical, stream a second no-follow raw comparison against the retained initial bytes through a fixed-size buffer and require the same identity as the still-live destination witness. For an absent snapshot, require exact `NotFound`. If a lock-unaware editor changed or replaced it, abort with `PublishedUnrecorded` and preserve the editor's path. This is a raw conflict check, not a second TOML parse or a second manifest-sized allocation.
7. On Windows, convert the flushed and validated temp writer into the only replacement-file handle allowed to survive the path syscall. Call [`ReOpenFile`](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-reopenfile) on the still-live writer with `dwDesiredAccess = 0`, `dwShareMode = FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, and `dwFlagsAndAttributes = FILE_FLAG_OPEN_REPARSE_POINT`. Require the returned witness to report the writer's exact volume/file identity, regular/non-reparse type, link count, and length. Then close the read/write writer. While the zero-access same-object witness remains live, perform one final temp path probe and the final canonical probe/raw comparison; both probes use `GENERIC_READ`, all three share flags, `OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT` and close before the publication syscall. An absent-snapshot canonical probe instead requires the exact no-follow `OpenOptionsExt`/metadata raw `ERROR_FILE_NOT_FOUND` or `ERROR_PATH_NOT_FOUND` result. The existing canonical snapshot handle, if any, remains live because `ReplaceFileW` opens the replaced file with all three share flags. This sequence is mandatory on both Windows branches; keeping the writer open, adding `DELETE`, or reopening only by pathname is not an alternative.
8. Use a manifest-specific same-directory wrapper selected only from the retained snapshot, with no `Path::exists()` branch. On Unix, rename while the validated writer remains open. On Windows with an absent snapshot, call [`MoveFileExW`](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-movefileexw) with exactly `MOVEFILE_WRITE_THROUGH`, without `MOVEFILE_REPLACE_EXISTING`; a newly appeared destination therefore fails. On Windows with an existing snapshot, call [`ReplaceFileW`](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-replacefilew) with `lpBackupFileName = NULL`, `dwReplaceFlags = 0`, and both reserved arguments null. `REPLACEFILE_WRITE_THROUGH` is explicitly unsupported and is forbidden, as are both ignore-merge flags. Convert both paths losslessly to absolute verbatim UTF-16 (`\\?\` for drives or `\\?\UNC\` for shares), reject interior NUL, and require the already-proven same parent and volume.
9. Capture the Boolean result and, on failure, `GetLastError` before any other Win32 call. On success and before closing either identity witness, no-follow reopen the canonical path with `GENERIC_READ`, all three share flags, `OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT`; require a complete regular/non-reparse file whose identity equals the zero-access temp witness, and on an existing snapshot require that the retained old destination witness still reports its original identity. The old destination handle may report link count zero after its name is removed; post-success validation must not reuse a helper that requires this retained, still-queryable handle to have exactly one link. A successful call followed by `NotFound`, a different final identity, an unsafe type, or an inspection error is `WindowsPostPublishIdentityConflict`; do not claim `Recorded`, delete any surviving name, or attempt rollback. Only after a successful postcondition may the new readable canonical handle replace the in-memory snapshot and the old destination and zero-access source witnesses close.
10. A failed `ReplaceFileW` enters the mandatory state machine below. Each inspection uses `GENERIC_READ`, all three share flags, `OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT` when readable, classifies both canonical and temp paths as `NotFound`, `Same(expected identity)`, `Different(actual identity)`, `Unsafe(type/reparse)`, or `InspectionError(raw error)`, and rechecks raw bytes when readable. Diagnostics include the decimal and hexadecimal raw error, canonical/temp paths, `backup = NULL`, expected `.ac`/lock/source/destination identities, all observed states, and whether the initial destination handle remains live. They never include manifest contents. No `ReplaceFileW` failure is retried automatically.

| Raw error | Documented namespace state with `backup = NULL` | Required recovery and cleanup |
| --- | --- | --- |
| `ERROR_UNABLE_TO_REMOVE_REPLACED` (1175) | Replaced and replacement files retain their original names. | Require canonical identity/raw bytes to equal the initial destination and the current transaction's temp identity/bytes to equal the source witness. Only that exact state permits the handle-bound current-owned cleanup protocol below. Any contradiction or inspection failure preserves both names and returns `WindowsReplaceRecoveryRequired`. |
| `ERROR_UNABLE_TO_MOVE_REPLACEMENT` (1176) | The replaced canonical no longer exists; the replacement remains under its temp name. | The temp may be the only named complete manifest. Never delete, promote, rename, or retry it automatically. Preserve it, report `WindowsReplacePartial::CanonicalRemovedReplacementAtTemp`, and require explicit user recovery. |
| `ERROR_UNABLE_TO_MOVE_REPLACEMENT_2` (1177) | The replacement remains under its temp name after inheriting destination streams/attributes; the old destination remains under a different, unspecified name. | Never delete, promote, rename, or search-and-delete either object automatically. Preserve the temp, retain both handle identities through inspection, report `WindowsReplacePartial::ReplacementEnrichedOldDestinationRenamed`, and require explicit user recovery. |
| Any other error | Microsoft documents that original names remain, while the replacement may still have inherited some attributes or streams. | Use handle-bound current-owned cleanup only when canonical identity/raw bytes equal the initial destination and temp identity/bytes equal the source witness. Otherwise preserve every name and return recovery-required diagnostics. |

The absent-snapshot `MoveFileExW` branch uses the same raw-error-first discipline. After any failed call, inspect both paths while the zero-access source witness remains live. Only exact `canonical = NotFound` plus `temp = Same(source identity and bytes)` proves a pre-publication state and permits the handle-bound current-owned cleanup protocol below. A canonical that now names the source identity, a missing or substituted temp, any other canonical object, or any inspection error is `WindowsMoveRecoveryRequired`; preserve every observed name, report the original raw error and expected/observed identities, claim no recorded publication, and never retry automatically.

11. Cleanup after a namespace failure is limited to the current transaction's owned temp in the exact proved states above. On Windows, while the zero-access source witness remains live, open the temp name no-follow with `GENERIC_READ | DELETE`, all three share flags, `OPEN_EXISTING`, and `FILE_FLAG_OPEN_REPARSE_POINT`; require the source identity, regular/non-reparse type, one link, expected length, and expected bytes; then call `SetFileInformationByHandle(FileDispositionInfo, FILE_DISPOSITION_INFO { DeleteFile = TRUE })`. Capture a zero-`BOOL` raw error immediately, then close the delete handle and the witness in that order. Any open, verification, or disposition failure preserves the name when possible and warns without masking the original namespace error. Path-based `DeleteFileW`, `remove_file`, or a close-then-delete sequence is forbidden because a substitution can otherwise redirect cleanup after proof. Every other current temp survives. A later Windows transaction inventories it as a prior recovery candidate and preserves it even if a valid canonical now exists; a later Unix transaction applies the step 2 valid-canonical identity proof. Never use temp contents to backfill or infer a publication timestamp.
12. After a successful Unix rename, call `sync_all` on the already pinned `.ac` directory handle and warn on failure. On Windows, successful temp `sync_all` is a pre-publication data-flush boundary only. `MoveFileExW(MOVEFILE_WRITE_THROUGH)` supplies its documented synchronous move behavior for the absent case; `ReplaceFileW` uses flags zero. Neither branch is claimed to flush the parent namespace or survive a kernel crash or power loss. Do not emit a per-write warning for this documented Windows limitation and do not infer durability from API success.

The local-NTFS atomicity contract is exact and separate from durability: a successful, postvalidated `MoveFileExW` or `ReplaceFileW` makes a new open of the canonical path observe either the complete old object before the namespace transition or the complete temp object after it; existing handles may continue to observe the old object. No atomic all-or-nothing claim applies to a failed `ReplaceFileW`, because errors 1176 and 1177 explicitly document partial namespace outcomes. Temp `FlushFileBuffers` completion precedes the namespace call, but Windows namespace/crash durability is not a v1 guarantee.

For an existing canonical on supported local NTFS, `ReplaceFileW` with flags zero is the metadata contract. The unnamed data bytes and final file identity come from the temp. The certified preservation surface is destination creation time, DACL, compression, and named streams not already present on the replacement; because the fresh temp is required to have no named user data stream, every destination ADS is preserved without a collision branch. The API also documents short-name, object-identifier, security-resource-attribute, and encryption behavior, but v1 does not independently claim or gate those properties. In particular, EFS-encrypted files are outside the certified support surface and receive no special code or acceptance path. Ordinary DOS bits such as `ARCHIVE`, `HIDDEN`, `SYSTEM`, and `NOT_CONTENT_INDEXED` are not promised. The independent clear-direction probe produced final `ARCHIVE` despite a clear destination, so even exact `ARCHIVE` preservation is false on the reference fixture; any observed equality for the other bits remains observational and cannot broaden the contract. Destination compression state wins over the fresh temp state, matching the documented merge behavior. The writer never clears read-only, never passes an ignore-ACL/merge flag, and never manually copies metadata; a read-only destination is refused before temp creation. A merge/access failure follows the error state machine. Owner, SACL, last-access/write/change time, ordinary DOS bits, extended attributes, sparse-state details, offline/recall flags, integrity/no-scrub flags, and every other excluded behavior are not independently promised. Stage E must pin creation time, read-only refusal, DACL, destination ADS preservation, and both compressed/uncompressed directions before Stage F. It must exercise set/clear ordinary-bit inputs as a non-guarantee regression and must not assert destination equality. Fixture setup uses only the direct bindings and explicit features named above.

For an absent canonical, the moved temp retains the security descriptor inherited when it was created in the pinned `.ac`, its attributes, streams, compression state, and its identity; there is no prior destination metadata to merge. EFS state remains outside the certified v1 surface. A destination that appears in the final window makes the no-replace move fail and is never overwritten.

One directory seed performs one initial canonical parse/validation, one pure in-memory merge, at most one streaming raw pre-replace comparison, and at most one temp-flush/publication sequence for the entire file set. It must never parse, flush, or publish once per row. The zero-access witness closes the confirmed read/write-handle conflict and keeps a same-object source identity live, but `ReplaceFileW` remains path-addressed. A noncooperating actor can still modify the temp object or substitute the temp, canonical, `.ac`, or lock pathname after the final probes and before/during the path syscall. Post-success identity validation detects some outcomes but cannot undo them. This accepted final instruction-level window is outside the cooperating-writer guarantee, and the manifest remains non-authoritative.

One guard may host sequential transactions without reacquiring its own lock. A coordinator that can publish both project contexts completes the target-plus-canonical attempt for each timestamp-bearing `Published` outcome before starting the next target, refreshing its in-memory/raw snapshot after a successful manifest replace. It must not batch both rows until the outer loop returns, because a later context error on a pre-existing project cannot erase an earlier surviving publication. Config scope replacement and multi-prefix lifecycle cleanup remain one transaction apiece.

### 6.3 Lock order

To prevent deadlocks and runtime starvation, the global order is:

1. Perform prompts, Git checks, network work, dirty checks, public live-session preflight, and any async read needed to build owned intent. Release every state, lifecycle, and `TeamConfigMutationGuard`. A session create may first reserve its existing selection ownership and insert its pending row, but the insertion's inner `SessionManagerState` guard is released before any filesystem wait. A deletion may take a short initial team guard solely to copy raw config bytes; it must drop that guard before the next step.
2. For config seed only, after the blocking worker token wins `begin()`, call `blocking_lock_owned()` on the cloned process-local `ConfigSeedLockState`. Acquire it without a `SessionManagerState`, settings, PTY, team-config, or project-file guard. Queued work owns only the `Arc`, never the mutex guard.
3. Acquire `ProjectSeedManifestGuard` in blocking work and load the canonical snapshot. No path may wait for this guard while holding `TeamConfigMutationGuard`.
4. Revalidate the pinned owner and target. Agent Matrix deletion may now acquire the outer `RwLock<SessionManager>` and then the single inner `RwLock<SessionManagerState>` for its deletion-only pending-inclusive snapshot, but releases both before the next lock. No other lifecycle path gains a manager lock under the project gate.
5. If and only if the logical mutation reads or writes team configuration, acquire `TeamConfigMutationGuard` after the project gate. Re-read and revalidate the exact team bytes and filesystem membership under both. CLI member, GUI team, and Agent Matrix deletion retain project then team through their logical config/filesystem commit, rollback journal, and manifest prune. GUI and CLI workgroup deletion use the project gate only. Team-config-only create or update paths may acquire the team guard without a project gate, but they may never call a manifest-aware helper or wait for the project gate until that team guard is dropped.
6. New-project registration may take `SettingsState::blocking_write` directly after the project gate for its synchronous refresh and save. Agent Matrix deletion may take `SettingsState::blocking_write` only after project then team are held and the manager snapshot guards are released. It removes only the two current live agent keys and releases settings before team/project release. No other deletion takes settings under these guards.

No settings, team-config, outer session-manager, inner `SessionManagerState`, coordinator-clock, local-config, PTY-manager, or lifecycle guard may be held while waiting for the project gate. No code may acquire `ConfigSeedLockState` while holding the project gate. `ProjectSeedManifestGuard`, `TeamConfigMutationGuard`, and every synchronous or Tokio lock guard are forbidden across an async `.await`; the narrowly enumerated state commits run to completion in blocking work under the audited order above. Config seed releases the global seed mutex and project guard before PTY spawn. Lifecycle commands release project and team guards before blocker diagnostics, coordinator-clock work, refresh, event publication, or any other await.

Selection ownership is classified separately from lock guards. A normal `CreateFinalizationTicket` retains its already-reserved finalization queue slot, coordinator admission permit, and create-ticket permit while the create awaits blocking preparation. An inline restore/restart retains the selection worker envelope and admission ownership already held by its transaction; it does not reserve a normal create ticket. These bounded ownership permits may precede and span `ConfigSeedLockState` and project-gate waits, but code under either filesystem guard may not acquire another selection permit, submit a coordinator job, call a `SelectionTransaction` commit or rollback method, or emit a lifecycle event. Agent Matrix deletion never acquires selection ownership. Therefore delete may take project gate -> manager snapshot -> release manager -> team -> settings while create takes manager briefly -> releases it -> project gate, with no cycle. If delete wins, its pending-inclusive recheck rolls staged targets back and releases the guards; if create wins, it releases the gate before PTY or finalization and the delete recheck still sees the pending workdir.

The latency policy is explicit. Preserve the current coordinator queue/admission/create-ticket capacities and their backpressure, so at most the current bounded number of normal create owners plus one inline worker transaction can wait. On mandatory responsive local filesystems, each project-gate poll is capped at 10 seconds. The global `ConfigSeedLockState::blocking_lock_owned` wait and synchronous staging/filesystem calls retain the current no-hard-wall-clock contract; they occupy blocking work, not a Tokio runtime worker. Do not claim the 10-second project-lock bound covers them and do not add a semantic seed timeout in this Epic. Inline restore/restart may therefore serialize later selection work while preparation is active. This accepted latency is measured by separate global-wait, project-wait, staging, and end-to-end timers, and the contention tests must prove queue permits remain bounded, deletion makes progress without selection admission, unrelated Tokio work remains responsive, and shutdown follows the bounded ownership protocol below.

Cancellation behavior is fixed. Every ordinary request is awaited through `run_blocking_owned`, and every session request through the tracker-integrated equivalent. Their atomic or mutex start gate makes pre-start cancellation authoritative; `AbortHandle` only asks Tokio to discard queued storage sooner, and no caller may bypass the wrapper by scheduling and immediately dropping a raw queued `JoinHandle`. Once `Started` wins, abort cannot stop the closure and no cancellation seam is consulted between gate acquisition and the target, metadata, rollback, or manifest commit. If an ordinary caller is then canceled, only its response join is detached: the closure itself runs the already-started critical section to typed completion, performs closure-owned cleanup and diagnostics, explicitly unlocks, and then returns. A task canceled before its start gate performs no filesystem/state mutation and acquires no global, project, settings, or session-manager guard even if Tokio later polls the no-op closure. Session work additionally remains tracker-accounted; ordinary work does not gain selection shutdown ownership. This rule applies to config seed, new-project setup, context materialization, explicit overwrite, and lifecycle work.

`SelectionCoordinator` owns session-create blocking work through `blocking_seed_work: Arc<BlockingSeedWorkTracker>` in `CoordinatorInner`; it is not Tauri managed state or public API, and both RAII halves retain the `Arc` so a deadline-retained worker cannot outlive its accounting state. Its `std::sync::Mutex` state contains `accepting`, a checked-monotonic `u64` id, and one map whose values are `Queued { abort: Option<tokio::task::AbortHandle> } | Started`, with a `tokio::sync::Notify` for quiescence. Mutex poison is recovered with `into_inner()` and an error log, never an `unwrap` or silent untracking. Id overflow atomically sets `accepting = false` and returns `selectionCoordinatorUnavailable`; ids are never reused.

Immediately before scheduling each session context or config closure, registration locks that one state, requires `accepting` and atomic coordinator phase exactly `Running`, inserts `Queued { abort: None }`, and returns two internal RAII halves; the current sequential create flow can have at most one id active per create. Checked id exhaustion changes `accepting` to false under that same mutex, schedules nothing for the failed registration, and leaves all prior ids tracked for sealing/quiescence. The tracker-integrated spawn obtains the blocking task's `AbortHandle` and attaches it under the same mutex. If cancellation/sealing or an already-completed worker removed the id, attachment calls `abort()` after unlocking; aborting a completed handle is harmless. If Tokio still starts the closure, its worker token observes the missing id and returns before acquiring any guard or mutating. If the worker already changed the entry to `Started`, attachment does nothing because blocking abort can no longer stop it. The await half stays in the create future. Dropping it removes only `Queued`, takes its abort handle, releases the tracker mutex, then calls abort; `seal` follows the same collect-under-lock, abort-after-unlock rule for every queued entry, including the attach race.

The worker token calls `begin()` under the same mutex before any mutation: it either changes `Queued` to `Started` or observes a missing id and returns without work. A successful `begin()` arms a `WorkerCompletionGuard` whose `Drop` is the sole normal/panic cleanup for that `Started` entry: it removes exactly its id under the poison-recovering mutex and notifies quiescence after unlocking. Scope resources so every global/project/settings guard, rollback/temp owner, and constructed typed result is dropped or completed before this completion guard; Rust unwinding from a blocking-closure panic must also drop the resource guards first and then remove/notify the tracker entry. The response waiter maps the panic to its existing join error, but shutdown cannot retain a ghost id. Once `Started` wins, dropping the await half cannot cancel or remove it. No tracker mutex is held while aborting, notifying, closing semaphores, taking another lock, or awaiting `Notify`. This map is the sole queued/started truth; abort is only a best-effort queued-storage optimization. If registration loses to closing/sealing, no closure is scheduled and the existing pending-create rollback path returns `selectionCoordinatorUnavailable` without PTY or events.

`close_and_join` preserves its five-second aggregate budget, finalization reserve, worker abort/join behavior, pending-create cleanup, container lifecycle sender shutdown/drain, retained-task storage, critical-key cleanup, and `SelectionShutdownReport` contract. Its ordering becomes: store `Closing`; seal the blocking tracker under the same registration mutex, remove queued entries, and abort their handles after unlocking; close admission/create-ticket semaphores; cancel the shutdown token; begin container shutdown; process the coordinator worker as today; then, before `cleanup_pending_creates_after_join`, wait for tracker quiescence only until the existing worker-phase deadline. Each loop creates the `Notify::notified()` future before taking the tracker mutex, rechecks the `Started` map under the mutex, drops the guard, and only then awaits, so completion cannot be lost between inspection and await. A clean report requires every `Started` entry to finish. At that deadline, do not pretend `spawn_blocking` was aborted: append exactly one `reason=blocking-seed-transaction-await state=retained` when any started id remains, making `persistence_safe = false`, and spend the preserved final reserve on the existing pending-create and container cleanup. The closure remains run-to-completion and may finish truthful target-before-manifest filesystem work, but it has no selection transaction authority. Because the outer create races the existing shutdown token, shutdown-winning normal and inline creates roll back their pending row exactly once, never finalize or retain a successful pending session, and publish no `session_created`, `session_destroyed`, or `session_switched` event after close wins; any PTY/container start already in flight remains owned by the existing pending/container cleanup path. Dedicated-runtime tests must release every finite blocking barrier before dropping their runtime, because Tokio waits indefinitely for started blocking tasks unless the test deliberately uses `shutdown_timeout`; production Tauri uses its process-global singleton runtime, so retained blocking work is ended only by normal completion or process termination, with process-death filesystem gaps classified by section 6.5 rather than by a false runtime-drop cancellation claim.

Application exit must never await the context-alert actor before that sealing step. `ContextAlertMonitor` adds an idempotent synchronous `request_close()` that cancels its token but does not take or await the join handle; `close_and_join()` calls `request_close()` for standalone safety and remains the sole consumer of the actor join. The exact exit order in `lib.rs` is: trigger the shared background shutdown token; call `context_alert_monitor.request_close()` when managed state exists; synchronously run `selection_coordinator.close_and_join()` to completion and record its report; only then run `context_alert_monitor.close_and_join()`; then continue existing PTY, resource-monitor, and global cleanup. The alert monitor remains sole owner of the actor, `InFlightSlot`, wrapper, nested delivery task, and completion reporting. Its join may remain unbounded, but it occurs only after selection is sealed, queued #1038 work is suppressed, and started #1038 work is either quiescent or truthfully retained.

The #1056 internal-notice wake route must make the real background create await cancellation-aware. Immediately before `phone::mailbox::spawn_wake_session`, retain the existing guard and absence rechecks, then use a biased `tokio::select!` between the attempt cancellation token and the existing `spawn_wake_session` future. Cancellation drops only the create response future; it does not spawn a second create task and does not detach or abort started blocking filesystem work. The existing `CreateFinalizationTicket` or inline owner rolls back a still-pending create exactly once, while `BlockingSeedWorkTracker` remains the sole queued/started filesystem owner. A create that already returned before cancellation remains an ordinary session owned by selection cleanup. The route must continue to call `commands::session::create_session_inner` with `CreateSelectionIntent::Background`; no alert-specific session constructor, raw `spawn_blocking`, or lifecycle owner is permitted.

`new_project_inner_with_settings_path` currently calls synchronous project filesystem setup while holding `SettingsState` for the entire `mutate_project_paths_with_settings_path` closure. Split it with an explicit same-project preparation protocol, not a naked unlock/relock: create or locate `.ac`, acquire/pin its project gate, and while holding it run `ensure_project_context_templates` with the borrowed guard for both newly created and pre-existing `.ac` roots so a prior partial setup cannot be registered as complete. Only then acquire `SettingsState` in the order above, re-refresh the disk-authoritative project list, and upsert/save. Preserve the current save-failure state contract too: the live in-memory project list remains deliberately mutated if its subsequent disk save fails, the valid `.ac` and truthful rows remain, and the command returns registration failure. Two same-project callers serialize once they reach the project gate, and each revalidates after acquisition. Winning `create_dir` records creation intent but never recursive deletion authority: another caller may use the same visible root and in-root gate without changing its identity. Any preparation failure leaves the root unregistered and preserves truthful partial templates/rows; cleanup is limited to identity-proved operation-owned temps. The project gate must not be held during Git operations, repo dirtiness checks, network clone work, user prompts, or PTY operations. Config and context publishers revalidate their target owner after every gate wait; a precomputed `ResolvedConfigSeed`, context directory, or deletion plan is intent only and never permission to recreate or mutate a path that disappeared or changed identity while waiting.

### 6.4 Corrupt, unsupported, and future manifests

- Missing canonical file: start empty, forward-only.
- Valid v1 with exact coverage: merge normally.
- `schema_version > 1`, unknown top-level/row fields, or a different coverage contract: preserve bytes and disable this writer. An old binary must not strip future data.
- Invalid TOML (including Git conflict markers, duplicate TOML keys/tables, and scalar/table redefinition), invalid UTF-8, duplicate identity, mixed source/time within a config scope, invalid path encoding, traversal-shaped path, malformed timestamp, kind/scope/source mismatch, or a size/row/field bound violation: preserve bytes and disable this writer. Do not fall back to `{}` and do not quarantine or rename the only copy automatically.
- Canonical path is a directory, symlink, junction, reparse point, or another non-regular type: do not follow or replace it.
- A target publication may still succeed while a locked manifest is read-only because its canonical bytes are corrupt or future-versioned. Log `PublishedUnrecorded`; do not synthesize a time later.
- Persistent degraded conditions use a process-local warn-once key of manifest path plus error class, with later repetitions at debug level. A post-publication write failure names the affected scope and states that the target succeeded but metadata did not.

### 6.5 Target-to-manifest crash gap

The target and manifest cannot be one filesystem transaction. V1 deliberately chooses no false positives over guaranteed completeness:

| Crash/failure point | Required state after restart |
| --- | --- |
| Before target publish | Old target and old manifest; no new row/time. |
| Target publish syscall fails without a committed logical removal | Old manifest; no new row/time. Publisher follows its existing rollback/skip/failure behavior. |
| Config old destination renamed to trash, process dies before new install or restore | Original config destination may be absent and the prior scope rows may be stale; no new row/time is created. The hidden old tree may remain until the existing scratch cleanup runs. V1 does not infer success, restore from the manifest, or invent a timestamp. |
| Config install fails and old-destination restore succeeds | Old target and old manifest; no new row/time. |
| Config install and restore both fail while this process survives | Return typed `FailedAfterLogicalRemoval(PreviousScopeStillStaged)`, remove the old scope in the already-held transaction, and add no row/time. If that prune itself fails, warn that old rows are stale; never call the failed install `Published`. |
| Target succeeds, process dies before manifest replace | New target may exist with old or missing manifest. Do not infer or backfill. Kernel lock is released automatically. |
| Coordinator shutdown wins while session blocking preparation is queued or active | A registration rejected after tracker sealing schedules no mutation. An already-started closure remains target-first and run-to-completion; clean shutdown waits within its existing worker-phase deadline, while deadline exhaustion reports retained ownership and unsafe persistence before pending/container cleanup continues. The pending session is rolled back and emits no lifecycle event. If process exit cuts the retained closure between target and manifest, this is the same accepted false-negative boundary, never a false row. |
| Manifest temp write/flush/`sync_all` fails before a namespace call | Target remains successful; canonical manifest remains old. Clean only the current transaction's owned temp after the same-identity cleanup proof; otherwise preserve and warn. |
| Lock-unaware editor changes canonical bytes after the initial snapshot | Raw pre-replace comparison aborts metadata publication; target remains successful and is reported `PublishedUnrecorded`. |
| Windows create-only `MoveFileExW` fails | Capture the raw error first and inspect canonical/temp identities while the source witness remains live. Clean the current transaction's owned temp only in the exact absent-canonical plus unchanged-temp state. Preserve every ambiguous or post-move-looking state, report `WindowsMoveRecoveryRequired`, do not retry, and do not claim a recorded publication. |
| Windows `ReplaceFileW` returns 1175 | Inspect both names and identities before cleanup. Only exact original-canonical plus the current transaction's exact temp permits owned-temp cleanup; otherwise preserve both and report recovery-required. |
| Windows `ReplaceFileW` returns 1176 | Canonical may be absent and the complete replacement remains at the temp name. Preserve it and require explicit recovery; every later Windows transaction treats it as a prior recovery candidate even if another valid canonical appears. |
| Windows `ReplaceFileW` returns 1177 | Replacement remains at the temp name with inherited metadata and the old destination has another unspecified name. Preserve all observed state and require explicit recovery; never retry or search-and-delete automatically. |
| Canonical namespace call succeeds and postvalidation succeeds, then the process dies without a kernel/power failure | The row is truthful because target success happened first. A new open observes the complete new canonical object. Existing pre-replace handles may still observe the old object. |
| Unix parent-directory sync fails | Keep the successful target and canonical replacement, emit a durability warning, and do not republish the target. |
| Windows process crash, kernel crash, or power loss around either namespace call | Process-kill behavior is tested, but v1 makes no namespace/crash-durability or power-loss guarantee. Temp data was flushed before the call; after reboot the canonical may be the old complete file, the new complete file, absent, or in a filesystem-recovered state. Preserve strict-invalid bytes, do not infer success, and do not backfill. No claim is derived from `REPLACEFILE_WRITE_THROUGH`; that flag is forbidden. |
| Lifecycle path becomes logically absent, process dies before prune | Stale rows may remain. Discovery and generic `NotFound` do not reconcile them; only a later explicit lifecycle event or actual scope publication can change them. The gate prevents a cooperating publisher from interleaving between the logical removal and prune while the process remains alive. |

No pending intent, startup reconciliation, or backfill is added in v1. For create-only files and byte-identical replacements, a recovered intent plus final byte equality cannot prove which process won. Ownership hashes, mtimes, Git history, and observed existence do not add that proof. Marking it committed would invent a potentially false timestamp. The next real publication heals a context row or replaces a config scope with its new actual timestamp; an `AlreadyPresent` or equal-default observation does not.

For config seed, every manifest error remains fail-soft for launch. The PTY starts. If the project gate timed out behind another cooperating writer, seeding is skipped rather than racing that writer. If the target already published and manifest persistence then failed, do not turn the launch into an error and do not retry the seed.

## 7. Compatibility, security, privacy, Git, and performance

### 7.1 Compatibility

- Existing installations start with no invented rows. Existing context files and ownership state are not backfilled.
- Pre-#1038 binaries ignore the new file and can publish without updating it. On downgrade, the manifest remains but may become stale. Re-upgrade still does not infer missing history.
- Future schema or coverage versions are preserved byte-for-byte by v1 writers.
- Public session visibility and selection compatibility are unchanged. Pending creates remain absent from `list_sessions`, `get_active_session`, websocket/Tauri lifecycle payloads, and the strict TypeScript `SessionSelection` decoder; the deletion-only snapshot never crosses IPC.
- #1028 discovery keeps backend `repo_dirty`, serialized `repoDirty`, and `SessionRepo.dirty` as backend-authoritative `Option<bool>`/`boolean | null`. #1032 context scraping keeps post-PTY registration, local/container screen-row support, and no frontend protocol addition.
- #1052 display behavior remains unchanged and display-only: trimmed, case-insensitive `PASSWORD*` keys are masked through `shouldMaskEnvValue`, every other environment value is shown in plaintext, and all values remain stored as plaintext. The existing `profile-utils.test.ts` mask/plaintext cases and both conditional SettingsModal password/text input sites remain intact; #1038 adds no frontend storage or transport behavior.
- There is no dependency on #958 and no schema migration between the two files. If #958 later generalizes ownership outcomes, its typed `Published` signal may feed this recorder, but its hashes, backups, classifiers, and overwrite decisions remain independent.
- A `Published` value is evidence emitted after an independently authorized write, never a capability fed backward into overwrite/delete authorization. Removing the manifest recorder or forcing it to fail must not change any #958 hash/classifier/backup decision or target bytes.
- The Windows client floor is the product's documented Windows 10 1809+, including Windows 11. Only local NTFS receives the section 6.2 writer and metadata claim. ReFS/CsvFS/FAT-family, Windows Server/Wine, and UNC/SMB remain unclaimed or opt-in exactly as the matrix states; a successful probe does not silently broaden support. A filesystem without working locks cannot claim the multiprocess guarantee.

### 7.2 Security and privacy

- Treat the manifest as untrusted project content. A valid-looking forged row can affect only diagnostic text on the next merge; it cannot cause stat, read, write, overwrite, repair, or delete outside the publisher's independently validated target. Project, `.ac`, lock, workgroup, replica, temp, and canonical identities are derived and revalidated from opened no-follow handles, never from a row or stale path spelling.
- On Windows, the zero-access `ReOpenFile` witness proves that the source identity held through the path syscall is the object that was written and flushed. The still-live destination snapshot proves the pre-call destination identity. Neither handle turns `ReplaceFileW` into a handle-addressed compare-and-swap; the final path substitution or same-object mutation window remains explicit, and a post-success mismatch is diagnostic failure rather than permission to delete or roll back an unknown object.
- Lifecycle filtering is pure metadata filtering against a validated scope prefix. It does not join a manifest row to the filesystem.
- Reject traversal and absolute identities. Do not call `canonicalize` on row-supplied paths and do not follow row-supplied reparse points.
- Existing context byte/hash checks remain the only permission for recognized automatic overwrite. A manifest row is never consulted for that decision.
- Commit only project-relative destination names and coarse source enum. Do not commit absolute project/source/config-dir paths, account names, machine ids, content hashes, file sizes, tokens, or file contents.
- Logs are local and may use the already-known project path for diagnosis, but must not log file contents or source tree enumeration.
- Windows partial-replace diagnostics may log canonical/temp paths, raw error numbers, and stable file identities, but never DACL contents, ADS contents, TOML bytes, account names discovered from an ACL, encryption keys, or source-tree contents.

### 7.3 Git behavior

- Persistent `.ac/.team-config-write.lock` Git ownership landed independently in #1070 through implementation commit `1c3d58d0375fad496ae34838ee67896b0165ec11` and PR #1071 at historical landing `0f7ec32e2d547a899036e1e6b2cfbab810fbfcf9`, now the parent merge base of the recomposed candidate. Its exact two-path outcome is the certified plan plus `src-tauri/src/commands/ac_discovery.rs`. It adds exactly the two-line managed block in section 4.1, preserves the lock file on guard drop, and proves create, byte-preserving append/idempotence, root Git provenance, and nested non-match. No seed-manifest rule or Cargo byte belongs to that completed repair.
- Stage A retains its separate seed-specific managed block exactly: anchored root lock/temp exclusions plus the root manifest negation. Candidate `c822e5ce4e07efd63e3a8d8771b745531bbffb2a` preserves both blocks without folding the team lock into Stage A's approved seed source patch; inherited #1072 changes no `.gitignore` code or rule.
- No-op discovery, registration, archive/unregister, context observation, ordinary failed/skip seed with no committed logical removal, and lost race produce no manifest diff. The separately typed failed-after-logical-removal case may only prune its proven staged-away prior scope.
- A successful config seed from tiers 1 through 4 sets every row to the spawn's shared millisecond timestamp. This normally creates a large but truthful diff; a same-millisecond identical state is byte-stable. Both behaviors are explicitly documented.
- A complete scope replacement makes removals reviewable: `{a,b} -> {b,c}` shows `a` removed, `c` added, and `b`'s time changed whenever the formatted event time differs.
- Array rows are sorted, so nondeterministic `read_dir` order cannot churn the file.
- User or parent Git rules may still hide `.ac`; AC documents but does not override a parent directory exclusion.

- Concurrent Git branches can conflict in a high-churn manifest. Conflict markers make the file strict-invalid and therefore read-only to AC until the user resolves the merge; AC preserves the conflicted bytes and continues target publications only under the documented `PublishedUnrecorded` degradation.
- Scale evidence records canonical byte size and `git diff --numstat` added/removed line counts plus diff generation wall time for 1k, 10k, and 100k rows. Every-spawn timestamp churn is a product cost, not an optimization target that may silently change time semantics.

### 7.4 Performance

- Manifest parse, validation, sort, and serialization are O(number of rows); one directory publication holds one in-memory state and performs one canonical replacement.
- The current global process-local config seed lock is retained, so config seeds in this process remain serialized even across projects. The additional per-project lock spans project-owned config staging, swap, and manifest commit to preserve current scratch cleanup and cross-process ordering; it does not serialize context/lifecycle publishers in unrelated projects.
- The 10-second bound covers project file-lock polling on responsive local storage. Total spawn preparation can be longer because it also includes the global `ConfigSeedLockState::blocking_lock_owned` wait and staging inside tracked blocking work. Measure global-seed wait, project-gate wait, and staging separately. A timed-out project gate is a launch-safe config skip.
- Large-tree coverage measures 1k, 10k, and 100k rows for both a small-scope mutation in a whole manifest and a whole-scope replacement. Report initial parse/validate, mutate/sort/serialize, temp write/flush, raw pre-replace comparison, Windows writer-to-witness transition and final probes, namespace call/postvalidation, any failure-state inspection, lock wait, lock hold, total wall time, peak additional working set, canonical bytes, and Git diff time/lines.
- Run end-to-end config staging for 1k, 10k, and 100k regular files and separate staging/swap cost from manifest cost. The 1k and 10k cases establish the growth curve and have correctness gates but no independent time threshold.
- Performance pass/fail accounting is fixed. In an isolated release-mode child on the documented Windows reference machine, each 100k small-scope mutation, 100k whole-scope replacement, and 100k end-to-end config staging plus manifest transaction must individually complete in at most 10 seconds and consume at most 512 MiB of additional working set. Each near-cap valid or invalid parser fixture is measured as its own operation against the same limits. Additional working set means the maximum resident/working-set sample during the operation minus the sample immediately before the operation. Fixture generation, child startup, deliberate 10-second contention waits, and the separate Git command are outside that interval; normal uncontended lock acquisition, parse, staging where applicable, mutation, serialization, file-data flush, Unix directory sync where applicable, raw comparison, and namespace publication are inside it. Record CPU, RAM, filesystem, Windows build, Rust version/profile, and Git version with the results. Any limit failure blocks Stage F; the limits cannot be raised inside an implementation PR.
- Git diff generation is required observational evidence, not a runtime gate: every 1k/10k/100k fixture must complete successfully and record elapsed time, canonical bytes, and `git diff --numstat`, but it has no numeric pass threshold because Git version and repository configuration are outside the AC writer. This is an explicit accepted product limit, not permission to suppress physical-publication timestamps or truncate rows.
- The plan permits one initial parse and one bounded streaming raw pre-replace comparison. Windows adds constant-size handle facts, stream inventory, witness, path-probe, and postcondition work, not a second parse or manifest-sized allocation. It does not add per-row flush, hash, destination rescan, or source/live-destination rescan. A no-op lifecycle mutation performs no temp write or publication call.
