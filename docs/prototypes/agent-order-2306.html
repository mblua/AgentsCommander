Prototype: coding-tool order — Settings and Step 1 (bug #2311 · epic #2306)

Static design mock. No application code, no IPC, no schema, no real settings files. Every save below is simulated in in-page state only; reloading the browser resets it.

Today reproduces the current behavior: Settings shows the saved vector order (Claude Code, Codex, Pi, Grok); Step 1 stays alphabetical (Claude Code, Codex, Grok, Pi) and has no move controls. Proposed starts both screens in the Settings order and shows up/down move controls in both — shown together only for comparison, not as an approved placement.

Decision for you: where should move controls live — Settings only, Step 1 only, or both?

Mock conditions (persistent settings.local.json ownership, transient save failure, stale expected-neighbour conflict) can be triggered from the toolbar. The disabled-by-ownership state is proposed production behavior: it assumes a read-only backend snapshot flag plus authoritative command rejection, and the current app exposes no such flag.
